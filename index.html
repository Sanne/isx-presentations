01

The isx model

You wouldn't hand a new hire your laptop — not even a clone of it

Three pillars

A real machine of their own

Full Linux workstation — own filesystem, init, networking, process tree. Everything works because it is a real system. Sudo works without a password — the agent can install any package, start services, tune sysctl, run Docker Compose, use strace. Full autonomy, zero babysitting.

Zero credential exposure

API keys and tokens never enter the environment in any form. A host-side TLS proxy injects credentials upstream.

A fresh one in seconds

Branch a template like you'd branch a repo — an instant CoW clone, booted and ready to work in. Need another? Branch again.

Total freedom inside the sandbox

The agent has root — on its own machine.

It can install profiling and diagnostic tools, craft its own, tune sysctl, start and stop services — and break any of it.

And there is nothing of value to steal. No real keys. No real tokens. No personal documents. No credentials worth selling.

The agent taints its own storage — but it's a cheap CoW branch. Destroy it. Branch a fresh one in seconds. The template stays clean.

02

Credential isolation

The agent never holds a real key

The problem with credentials

  • Env vars? Readable by any process
  • Mounted files? Cat-able, exfiltrable
  • Credential helpers? Agent can call them
  • BASE_URL wrappers? Agent can bypass them
  • OAuth tokens? Better — scoped and expiring — but can still leak to other systems

Every approach that puts credentials inside the container
leaves an attack surface inside the container.

isx: credentials never enter

The container trusts the proxy's CA, which is what lets the proxy terminate TLS and rewrite the header. The real credential stays on the host — we never hand it to the container.

03

Copy-on-write branching

The git metaphor for environments

You know git worktrees

Worktrees let you check out multiple branches side by side — each gets its own working directory. Great for parallel work on source code.

But a worktree only isolates files in the repo. Everything else is shared:

  • Dependencies — node_modules, ~/.m2, pip packages, SNAPSHOT JARs
  • Installed software — JDK version, system libraries, CLI tools
  • Running services — databases, Docker containers, dev servers
  • Ports & networking — port 8080 is port 8080 is port 8080

isx branching for the entire machine

Source code, dependencies, installed packages, running services, open ports, environment variables, the entire filesystem — all isolated, all snapshotted, all instant.

Build once, branch instantly

tpl-java (stopped template, ~2 GB) ├── fix-nasty-bug (running, ~50 MB extra) ├── review-pr-423 (running, ~30 MB extra) └── experiment (stopped, ~10 MB extra)
  • Template — a pristine environment, specified declaratively
  • Branch — a booted copy. The moment an agent touches it, it is tainted
  • An instant CoW clone (btrfs/zfs/lvm), with its own independent filesystem
  • Not a verdict on what the agent did — you simply can't prove what it changed
  • So you never clean one up: destroy it, branch a fresh one
  • The template and every other branch stay completely unaffected

Storage: shared, not copied — but isolated

Shared base blocks — stored once (~2 GB)
fix-bug ~50 MB review-pr ~30 MB experiment ~10 MB agent-4 ~40 MB

Without CoW

10 branches × 2 GB = 20 GB

With CoW

2 GB shared + deltas = ~2.4 GB

Git shares objects between branches. isx shares blocks between machines — the same trick, one layer down, and why a whole machine is about as cheap to branch as a repo.

Getting work back out

Standard git fetch, git push, git pull — directly to containers. isx handles all the wiring. 

# The agent works inside the container, makes commits...

# On the host — review and cherry-pick, like any teammate's work:
git fetch fix-auth
git diff main..fix-auth/main
git cherry-pick fix-auth/main

Fully managed

Remotes are added on branch, removed on destroy — zero manual setup

Immutable snapshots

You act on a specific commit, not a live directory the agent can still change

Templates & tools

Composable, cacheable, declarative

Define a template in YAML

name: tpl-quarkus
description: Quarkus development box
parent: tpl-mydev
tools:
  - podman
  - graalvm
  - mvnd
  - claude: {model: claude-sonnet-5}
default-action: claude
packages:
  - unzip
repos:
  - url: https://github.com/quarkusio/quarkus.git
    prime: mvnd -b singlethreaded -Dquickly
  - url: https://github.com/quarkusio/quarkus-quickstarts.git
    path: ~/quarkus-quickstarts

Templates inherit from a parent; tools compose independently and can take parameters.

Built-in tools

AI agents

claude, pi, bob, codex

Build tools

maven-3, mvnd, podman

IDE integration

VS Code Remote, JetBrains Gateway

Dev infra

sshd, tmux, zmx, starship

Define your own tools as YAML — packages, downloads, proxy rules, TUI actions.

Host resources

host-resources:
  - source: ~/.gitconfig         # your aliases, identity, settings
    mode: readonly               # default — safe, read-only
  - source: ~/datasets/training
    mode: overlay                # read-only base + writable layer

readonly

Read-only bind mount. Share config files, reference data.

overlay

Host data + ephemeral writable layer. Agent sees read-write; host is fully protected.

Share config, datasets, or large assets without copying into every branch.

The workflow

From setup to review

Day-to-day flow

once isx build tpl-quarkus — JDK, Maven repo warmed, repos cloned, tools installed
↓ branch as many times as you need
parallel isx branch fix-auth → agent codes • mvn verify • commits → review → destroy
isx branch add-tests → agent codes • mvn verify • commits → review → destroy
isx branch bump-quarkus → agent codes • mvn verify • commits → review → destroy
↓ deps move on, upstream moves on
now and then isx build tpl-quarkus — re-run it; every branch from here starts current

Dependencies are installed once in the template, so every branch starts with them already in place — and refreshing the template is the same one command that built it.

Network modes

Mode Flag What it does
Full internet (default) Unrestricted access, auth via proxy
Proxy only --proxy-only Traffic restricted to MITM proxy only
Airgapped --airgap Network device removed, total isolation

Runtime modes

Mode Flag What it does
Container (default) System container — shared kernel, near-native speed, instant startup
VM --type vm Full virtual machine — separate kernel, hardware-level isolation
KVM --type kvm VM with /dev/kvm passthrough — nested virtualization inside the VM

Containers are the practical default — near-native performance, instant CoW branching, minimal overhead. VMs add kernel-level separation as defense in depth — for higher security requirements or compliance mandates.

Custom proxy credentials for any service

Declare a YAML tool — any HTTPS API gets transparent auth, no config inside containers. 

name: artifactory
proxy:
  config-namespace: artifactory
  configuration:
    token: { config-path: "token", secret: true }
  auth:
    - domains: [artifactory.internal.example.com]
      type: bearer
      token: "${token}"

Supports bearer, basic, and custom header auth. Wildcard domains supported. isx init prompts for credentials.

Session persistence: zmx

Persistent terminal sessions that survive disconnections — with native scrollback and multi-client support. 

# Sessions appear natively on the host (Linux)
zmx list                        # shows isx-my-branch

zmx run isx-my-branch git status # run a command
  • Auto-attaches on shell entry — every session is persistent by default
